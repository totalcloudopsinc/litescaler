# lite-scaler

Автоматическое масштабирование группы узлов Yandex Cloud Managed Kubernetes. Увеличивает размер
группы узлов фиксированного размера (`fixed_scale`), когда есть
подходящие поды в состоянии `Pending`, и уменьшает её, когда узлы
простаивают.

---

## Как это работает

Сервис — это веб-приложение на FastAPI с фоновым циклом опроса, который каждые
`poll_interval_seconds` (по умолчанию 30) секунд оценивает состояние кластера и при необходимости
меняет размер группы узлов.

### Масштабирование вверх

**Фоновый цикл** получает список подов в состоянии `Pending` в заданном
пространстве имён, которые соответствуют хотя бы одному из настроенных
селекторов (tags) **и ещё не назначены на узел** (нет `nodeName`). Поды, которые
уже находятся на узле, но «застряли» (`ImagePullBackOff`, циклический перезапуск
и т. п.), остаются в `phase=Pending`, но **не** требуют новых мощностей, поэтому
игнорируются.

Если число действительно неназначаемых подов превышает `pending_pod_threshold`
(по умолчанию `0` — достаточно одного пода в `Pending`), сервис:

считает нужное число узлов **двумя способами** и берёт большее:

1. **По спросу.** Суммирует запросы CPU/памяти (`requests`) подов;
   **смотрит свободную ёмкость на уже готовых (`Ready`) узлах группы** — только
   что добавленный узел становится `Ready` раньше, чем планировщик размещает на
   нём ожидающие поды; учёт его свободного места не даёт добавить второй узел под
   поды, которые поместятся на первом; делит оставшийся спрос на ёмкость одного
   узла **управляемой группы** и добавляет запас `headroom` (по умолчанию 15 %).
2. **По размещению.** Свободная ёмкость — не общий пул: под запускается только
   там, где **на одном** узле хватает места под весь его запрос. Поэтому поды
   раскладываются (сначала самые крупные) по свободному месту каждого узла
   по отдельности, а всё, что никуда не влезло, открывает новый узел. Семь узлов
   по 1440m свободных дают 9480m суммарно и при этом не могут принять один под на
   2000m — по спросу такой под выглядит удовлетворённым и остаётся в `Pending`
   навсегда, поэтому счёт по размещению перекрывает счёт по спросу.

Затем размер группы меняется до `current + nodes_needed` (с ограничением
`max_size`). Если поды помещаются в существующую свободную ёмкость, сервис ничего
не делает. Под, запрашивающий больше, чем целый узел, помечается в логе как
неразмещаемый и исключается из обоих расчётов — никакой размер группы его не
запустит.

### Учитывается только управляемая группа

Все показатели ёмкости берутся исключительно с узлов с меткой
`yandex.cloud/node-group-id=<node_group_id>`: размер одного узла (делитель
спроса), вычитаемая свободная ёмкость, проверка готовности группы и подсчёт
пустых узлов при масштабировании вниз. В кластере с несколькими нод-группами узел
чужой группы (например, небольшой системной) не должен задавать делитель — иначе
группа будет расширена с ошибкой во столько раз, во сколько различаются размеры
узлов. Узлы одной группы Yandex создаются по одному шаблону, то есть одинаковы;
если они всё же различаются, берётся **наименьший** — так ошибка возможна только
в сторону лишнего узла, а не нехватки. Если в группе вообще нет узлов в состоянии
`Ready` (масштабирована в ноль), используется `node_capacity_fallback` и пишется
предупреждение в лог.

### Масштабирование вниз

Когда ни один подходящий под не был в `Pending` в течение
`scale_down_cooldown_polls` последовательных опросов (по умолчанию 3), цикл
считает **пустые** узлы группы — узлы `Ready`, на которых нет ни одного
назначенного пода, соответствующего селекторам, — и уменьшает размер группы
на это число, вплоть до `min_size` (по умолчанию 0; разрешает
полностью пустую группу).

Так как группа `fixed_scale` масштабируется по количеству, Yandex Cloud сам
выбирает, какой узел вывести из эксплуатации (с корректным drain). Мы уменьшаем
размер только когда подходящие нагрузки полностью простаивают, поэтому любой
выводимый узел безопасен. Любой подходящий под в `Pending` подавляет
масштабирование вниз и сбрасывает таймер — масштабирование вверх всегда в
приоритете.

### Без повторного заказа узлов

Мощности никогда не заказываются дважды под одни и те же поды, потому что каждый
опрос заново выводит решение из **текущего** состояния кластера:

- пока изменение размера выполняется, цикл вообще ничего не делает (см. gate
  стабильности ниже), поэтому поды, ждущие ещё создающиеся узлы, не могут вызвать
  повторное масштабирование;
- когда эти узлы становятся `Ready`, их свободное место учитывается, поэтому поды,
  которые планировщик ещё не разместил, уже помещаются — и новые узлы не
  заказываются.

Под, который **всё ещё** неразмещаем после завершённого изменения размера,
поэтому рассматривается заново, а не считается «уже обработанным»: выданная
мощность ему не подошла, и вечное подавление такого пода оставило бы его в
`Pending` навсегда при отчёте сервиса «no action».

### Ожидание выполняющихся изменений размера (gate стабильности)

Группа `fixed_scale` сразу сообщает свой *желаемый* размер — ещё до того, как узлы
реально присоединятся (или завершат удаление). Действия на основе этого
нереализованного размера заставляют сервис «бороться» с собственной операцией:
добавлять второй узел до прихода первого или удалять только что добавленные узлы,
на которые ещё не успели попасть поды.

Поэтому перед **любым** изменением размера цикл проверяет, что группа достигла
желаемого размера (число `Ready`-узлов группы == желаемому) и что предыдущая
операция изменения размера завершена. Пока изменение размера выполняется, сервис
ждёт и ничего не делает.

### Ручное управление

Эндпоинт `POST /evaluate` — это **ручное переопределение**: вы указываете точное
число узлов для добавления, и сервис увеличивает группу на это значение (всё ещё с
ограничением `max_size`). Он не обращается к очереди ожидающих подов — эта
автоматика остаётся в фоновом цикле.

## Предварительные требования

### 1. Сервисный аккаунт и IAM-роли

Сервису нужен сервисный аккаунт (SA) Yandex Cloud с JSON-ключом авторизации.
Аккаунту нужны **две разные роли**:

- **`k8s.editor`** (облачная IAM-роль) — чтобы менять размер группы узлов. Сервис
  изменяет размер через gRPC-API Yandex Cloud (`NodeGroupService.Update`), поэтому
  это роль уровня облака, а не Kubernetes.
- **`k8s.cluster-api.cluster-admin`** — выдаётся SA как IAM-роль; именно она
  позволяет полученному IAM-токену обращаться к Kubernetes API. Более узких ролей
  `viewer`/`editor` **недостаточно**: они отображаются на ClusterRole `view`/`edit`
  в Kubernetes, которые покрывают только ресурсы в пространствах имён, тогда как
  сервис читает ресурсы уровня кластера — `nodes` и поды во всех пространствах
  имён.

Пример выдачи ролей на уровне каталога:

```bash
yc resource-manager folder add-access-binding <FOLDER_ID> \
  --service-account-id <SA_ID> --role k8s.editor

yc resource-manager folder add-access-binding <FOLDER_ID> \
  --service-account-id <SA_ID> --role k8s.cluster-api.cluster-admin
```

JSON-ключ создаётся так:

```bash
yc iam key create --output sa-key.json --service-account-id <SA_ID>
```

### 2. Группа узлов фиксированного размера

Управляемая группа узлов должна использовать политику **`fixed_scale`**, а не
автомасштабирование Yandex Cloud. Если на той же группе включён облачный
cluster-autoscaler, два контроллера будут конфликтовать за один ресурс — сервис
рассчитывает на `fixed_scale`.

### 3. Сеть: исходящий трафик для узлов

Узлам нужен исходящий доступ, чтобы скачивать образы (например, из
`cr.yandex`). Если узлы создаются **без публичного IP**, у их подсети должен быть
**NAT-шлюз** и **таблица маршрутизации** с маршрутом по умолчанию на него — иначе
любое внешнее соединение завершается таймаутом (`i/o timeout` при pull образа),
даже если группа безопасности разрешает исходящий трафик.

```bash
# NAT-шлюз (тип egress — это значение по умолчанию, отдельного флага нет)
yc vpc gateway create --name egress-nat

# Таблица маршрутизации с маршрутом по умолчанию на шлюз
yc vpc route-table create --name egress-rt --network-id <NET_ID> \
  --route destination=0.0.0.0/0,gateway-id=<GATEWAY_ID>

# Привязать таблицу к подсети группы узлов (повторить для каждой подсети группы)
yc vpc subnet update <NODE_SUBNET_ID> --route-table-id <ROUTE_TABLE_ID>
```

Также убедитесь, что группа безопасности узлов разрешает исходящие соединения по
TCP 443 (реестр образов) и стандартный внутрикластерный трафик.

> Если узлам выдаётся публичный IP на каждый узел, помните про квоту
> `vpc.externalAddressesCreation.rate`: быстрое добавление многих узлов может её
> превысить. Вариант без публичных IP (NAT-шлюз) безопаснее и не упирается в эту
> квоту.

### 4. Секрет с ключом и конфигурацией

При запуске в кластере положите `sa-key.json` в Secret и смонтируйте его. Путь в
`config.yaml` должен быть **абсолютным** и совпадать с точкой монтирования
(например, `/secrets/sa-key.json`) — относительный путь не найдётся внутри пода.

## Конфигурация

Отредактируйте `config.yaml` (образец — в репозитории). Основные поля:

- `yandex_cloud.service_account_key_file` — путь к JSON-ключу SA.
- `yandex_cloud.node_group_id` — управляемая группа узлов для масштабирования.
- `yandex_cloud.cluster_id` — идентификатор кластера Managed Kubernetes
  (используется для получения адреса master и CA-сертификата).
- `yandex_cloud.master_endpoint` — `internal` (по умолчанию; сервис работает как
  под и обращается к master по внутреннему адресу) или `external` (запуск вне
  кластера).
- `kubernetes.namespace` + `kubernetes.label_selectors` — какие поды `Pending`
  учитывать (под учитывается, если совпадает с **любым** селектором — логика OR).
- `scaling.max_size`, `min_size`, `pending_pod_threshold`, `headroom`,
  `scale_down_cooldown_polls`, `poll_interval_seconds`, `dry_run`.
- `scaling.log_level` — `INFO` (по умолчанию) логирует каждый шаг принятия
  решения; `DEBUG` добавляет разбивку по каждому поду и каждому узлу.

### Разбор решений по логам

Каждый шаг, влияющий на решение, пишется в лог, поэтому установку с
`dry_run: true` можно разобрать по одному логу. Один цикл опроса на уровне `INFO`
читается сверху вниз:

```
2026-08-14 09:12:41+0000 INFO    app.service: --- evaluate: group=cat-ml-gpu ns=default selectors=['tag=demo'] dry_run=True
2026-08-14 09:12:41+0000 INFO    app.k8s: Pending pods in ns=default: 3 total, 3 match ['tag=demo'], 3 still unscheduled
2026-08-14 09:12:41+0000 INFO    app.service: Pending pods: 3 unscheduled
2026-08-14 09:12:41+0000 INFO    app.k8s: Ready nodes in group cat-ml-gpu: 2 (cluster has 4 nodes in total)
2026-08-14 09:12:41+0000 INFO    app.service: Node group state: desired size 2, ready nodes 2, resize operation in progress: False
2026-08-14 09:12:41+0000 INFO    app.service: Pending pods request 24000m cpu / 48.00Gi memory in total
2026-08-14 09:12:41+0000 INFO    app.k8s: Node capacity of group cat-ml-gpu: 16000m cpu / 64.00Gi memory per node (from 2 Ready node(s))
2026-08-14 09:12:41+0000 INFO    app.k8s: Free capacity across 2 Ready node(s) of group cat-ml-gpu: 20000m cpu / 96.00Gi memory in total, largest single node 10000m cpu / 48.00Gi memory
2026-08-14 09:12:41+0000 INFO    app.scaling: decide: pending=3 (threshold 0), requests 24000m cpu / 48.00Gi memory, free in group 20000m cpu / 96.00Gi memory across 2 node(s), ...
2026-08-14 09:12:41+0000 INFO    app.scaling: decide: packing 3 pending pod(s) onto per-node free capacity ['10000m/48.00Gi', '10000m/48.00Gi'] -> 1 new node(s) needed, 0 pod(s) too big for any node
2026-08-14 09:12:41+0000 INFO    app.scaling: decide: unmet demand after free capacity: 4000m cpu / 0.00Gi memory -> 0.25 nodes by cpu, 0.00 nodes by memory; max * (1 + 0.10 headroom) = 0.28 -> ceil = 1; packing needs 1 -> 1 nodes needed

2026-08-14 09:12:41+0000 INFO    app.service: dry_run enabled; skipping resize to 3
```

Каждая строка содержит время, уровень и имя
логгера; собственные строки uvicorn (запуск и access-лог) получают такую же
отметку времени.

На уровне `DEBUG` дополнительно выводятся: каждый ожидающий под с его `requests`,
каждый узел группы с разбивкой allocatable / запрошено / свободно и имена узлов за
каждым счётчиком. Всё, что может незаметно исказить решение — отсутствие
`Ready`-узлов в группе, узел без allocatable, разные размеры узлов внутри группы,
под, не помещающийся ни на один узел — пишется как `WARNING`.

### Подключение к кластеру

Сервис подключается к Kubernetes **полностью через API Yandex Cloud** — он
не читает kubeconfig и не использует RBAC сервисного аккаунта пода. При запуске он
обращается к API Managed Kubernetes с ключом SA, получает адрес master-ноды и
CA-сертификат, и выпускает IAM-токен (автоматически обновляемый до истечения
срока) для аутентификации каждого запроса.

## Развёртывание в кластере (Terraform + Kustomize)

Каталог `deploy/` выполняет установку «в один клик» по окружениям. Работа
разделена по тому, кому нужен API Yandex Cloud и что безопасно хранить в Git:

- **Terraform** (`deploy/terraform/`) создаёт облачную часть — отдельный сервисный
  аккаунт, его две IAM-роли (`k8s.editor` + `k8s.cluster-api.cluster-admin`,
  см. [Предварительные требования](#1-сервисный-аккаунт-и-iam-роли)), ключ SA и
  Kubernetes-`Secret` (`lite-scaler-sa`), который этот ключ несёт. Кластер и
  группа узлов **уже существуют** — Terraform только ссылается на них.
- **Kustomize** (`deploy/kustomize/`) владеет манифестами — `base/` (Deployment +
  `config.yaml` по умолчанию) и по одному оверлею на окружение
  (`overlays/{dev,prod}/`), задающему `config.yaml` и тег образа для
  конкретного окружения.

```
deploy/
  install.sh                 # terraform apply + kubectl apply -k
  terraform/                 # SA, IAM-привязки, ключ, kubernetes_secret
    envs/{dev,prod}.tfvars
  kustomize/
    base/                    # deployment + базовый config.yaml
    overlays/{dev,prod}/   # config-patch.yaml + тег образа на окружение
```

Для каждого окружения отредактируйте `terraform/envs/<env>.tfvars`,
`kustomize/overlays/<env>/config-patch.yaml`, `kustomization.yaml` этого оверлея
и его `deployment-patch.yaml` (`nodeSelector`, который закрепляет сервис за
**стабильным** узлом — не за управляемой группой, иначе масштабирование вниз
может вытеснить сам сервис) — заменив плейсхолдеры `REPLACE_`. Затем:

```bash
# Достаточно авторизовать `yc` CLI как оператора. install.sh сам выпускает
# YC-токен и направляет kubectl на кластер (get-credentials --external).
./deploy/install.sh prod plan     # terraform plan + офлайн-сборка kustomize + best-effort dry-run
./deploy/install.sh prod          # terraform apply + kubectl apply -k
./deploy/install.sh prod destroy  # kubectl delete -k + terraform destroy (в обратном порядке)
```

Подробности и обоснование разделения — в [`deploy/README.md`](deploy/README.md).

### Альтернатива: вручную через kubectl

Пример манифеста — `examples/deployment.yaml`. Перед `kubectl apply`:

```bash
# Secret с ключом SA
kubectl create secret generic lite-scaler-sa \
  --from-file=sa-key.json=./sa-key.json -n kube-system

# ConfigMap с конфигурацией
kubectl create configmap lite-scaler-config \
  --from-file=config.yaml=./config.yaml -n kube-system

kubectl apply -f examples/deployment.yaml
```

## Эндпоинты

- `GET /healthz` — проверка живости.
- `GET /status` — текущая конфигурация и последнее решение.
- `POST /evaluate` — вручную добавить заданное число узлов (с ограничением
  `max_size`, если не включён `dry_run`). Требует JSON `{"nodes_to_add": N}`,
  где `N >= 1`; отсутствующее или неположительное значение возвращает `422`.

```bash
curl -X POST localhost:8000/evaluate \
  -H 'Content-Type: application/json' \
  -d '{"nodes_to_add": 3}'
```

## Метрики

Метрики Prometheus отдаются на отдельном порту (по умолчанию `9090`), отдельно
от API, поэтому цель скрейпа никогда не пересекается с `/evaluate`:

```yaml
metrics:
  enabled: true
  port: 9090
```

```bash
curl localhost:9090/metrics
```

Базовый Deployment объявляет порт `metrics` и аннотации пода
`prometheus.io/{scrape,port,path}`, так что кластер со скрейпом по аннотациям
подхватывает под без дополнительной настройки.

Экспортируются входные данные решения (pending-поды и их спрос по CPU/памяти,
свободная ёмкость группы, размер ноды), состояние группы (desired-размер,
Ready-ноды, идущий резайз, границы из конфига, `dry_run`), сами решения
(`direction` x `result`, добавленные и снятые ноды, оценки, пропущенные
гейтом) и здоровье цикла (ошибки YC API по операциям, минтинг IAM-токенов,
итерации, ошибки и длительность poll-а, время последнего poll-а, build info).

Полный справочник метрик, настройка скрейпа, правила алертов и запросы для
дашборда — в **[MONITORING.md](MONITORING.md)**.
